# Repository presentation decisions

The repository should let a new user understand the problem, inspect the real product, reproduce installation and judge limitations. A polished README alone does not establish production maturity.

| Reference | Principle adopted here | Concrete delivery |
|---|---|---|
| [Orbital](https://github.com/zqiren/Orbital) | Explain project continuity through a specific problem and show where state lives | README problem statement, local event-store architecture and recovery guide |
| [Magpie](https://github.com/yetone/magpie) | Put real product presentation, installation and language choices near the beginning | Shipped white UI, real screenshots, release download, English and Simplified Chinese READMEs |
| [Task Master](https://github.com/eyaltoledano/claude-task-master) | Make task-management workflows and integration entry points easy to find | Five-workflow guide, CLI/MCP setup and explicit Codex boundaries |
| [Agentic Project Management](https://github.com/sdi2200262/agentic-project-management) | Separate onboarding, workflow explanation and detailed guidance | Quick start, user guide, architecture and contribution instructions |
| [Zed](https://github.com/zed-industries/zed) | Ask contributors for reproducible changes and relevant validation | Issue/PR templates, contributing guide and actual CI |

These are presentation references, not endorsements or claims of feature equivalence. No upstream application code, screenshots or branding were copied. Popularity does not prove quality or compatibility. The product name describes its intended search category; discovery and ranking are not guaranteed.
